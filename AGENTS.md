# AGENTS.md — правила работы агентов в этом репозитории

Этот файл подхватывается автоматически в каждой сессии. Он адресован **основному агенту** — тому, кто общается с владельцем проекта.

> **Примечание для субагентов.** Если вас запустили на конкретную задачу этапа — вы исполнитель, а не основной агент. Ваша работа: выполнить задачу, лично проверить результат по критериям приёмки из вашего задания и вернуть подробный отчёт. Никакой инфраструктуры оркестрации от вас не требуется — только аккуратное исполнение и честная проверка.

## Цель проекта

Pet/open-source продукт: трекер задач LeetCode с интервальным повторением. Любой может склонировать репозиторий и запустить его локально одной командой (`docker compose up`). Позиционирование — **local-first**: данные пользователя живут только на его машине. Монетизации и облачного деплоя нет, но архитектура **container-ready**: проект можно развернуть на собственном сервере, изменив только `.env`. Назначение проекта — портфолио и опыт.

## Стек

- **Frontend**: React + Vite + TypeScript, Tailwind CSS v4, Vitest + Testing Library (`frontend/`).
- **Backend**: Java + Spring Boot (Web, Data JPA, Validation, Security), Flyway, PostgreSQL (`backend/`).
- **Инфраструктура**: Docker / docker-compose, GitHub Actions (CI).
- **Email**: `spring-boot-starter-mail`; SMTP из env, при незаданном SMTP — fallback с OTP в лог; локально — опциональный Maildev.

При противоречиях выше стоящий источник побеждает. После завершения этапа обновлять FRONTEND_CURRENT_STATE.md и раздел 9 PRODUCT_SPECIFICATION.md.

## Работа с git

- Перед началом каждого этапа от `main` создаётся новая ветка: `git checkout -b stage/<номер>-<краткое-название> main`. Вся работа этапа — только в этой ветке.
- Коммиты — в эту ветку, осмысленные сообщения по соглашению репозитория (conventional commits).
- В конце этапа — PR в `main`.
- Слияние только как **Squash and merge** (история `main` остаётся линейной, весь этап — один коммит).
- После слияния обязательно: удалить ветку этапа — и удалённую (`git push origin --delete`), и локальную (`git branch -d`), синхронизировать локальный `main` с `origin/main`. Только после этого начинать следующий этап.

## Процесс работы по этапам

Работа строго поэтапно по ROADMAP.md. Один этап за раз, новый этап не начинается, пока текущий не закрыт.

### 1. Постановка задачи субагенту

Основной агент не выполняет этап сам. Он формирует задание субагенту (coder), в которое **обязательно** входят:

- контекст: цель этапа, ссылки на соответствующие разделы ROADMAP.md и канонических документов;
- точные требования: какие файлы/модули трогать ожидается, каких соглашений придерживаться (стиль кода вокруг, структура пакетов, контракт API);
- **все критерии приёмки целиком** — включая критерий выхода этапа и команды проверки (`./gradlew test`, `npm run typecheck && npm run lint && npm run test` и т.п.). Критерии из ROADMAP.md переносятся в задание дословно, без сокращений;
- требование отчёта (см. ниже).

Чем полнее постановка, тем меньше недопониманий и возвратов.

### 2. Исполнение и самопроверка субагентом

Субагент выполняет задачу и **лично проверяет** результат: прогоняет указанные команды проверки, убеждается, что критерии выхода выполнены, что сценарий работает end-to-end, а не только компилируется. Незаконченную или непроверенную работу сдавать нельзя — если проверка не проходит, субагент исправляет сам.

### 3. Отчёт субагента

По завершении субагент возвращает структурированный отчёт:

- что сделано по пунктам;
- какие файлы созданы/изменены и зачем (кратко, по файлу);
- какие команды проверки запускались и их итог (с ключевыми строками вывода, не просто «ок»);
- как выполнен каждый критерий приёмки — по одному пункту;
- открытые вопросы, отклонения от задания, риски, которые субагент заметил сам.

### 4. Роль основного агента после отчёта

Основной агент **не перепроверяет реализацию по умолчанию**. Он знакомится с отчётом и оценивает его здраво смыслом. Личную проверку основной агент делает только в исключительных случаях:

- в отчёте виден потенциальный подводный камень: противоречие документам, подозрительное упрощение, несовпадение с контрактом, «проверка прошла», но сценарий выглядит недопокрытым;
- изменение касается критичной инфраструктуры (миграции БД, auth, контракт API), где ошибка дорога.

Личную проверку основной агент выполняет **сам** (прочитать файл, запустить команду), а не через нового субагента. Баланс важен: не проверять каждый пук, но не пропустить системный риск. Претензии по качеству на этом этапе — повод улучшить постановку задачи для следующих этапов, а не перелопачивать работу субагента.

### 5. Закрытие этапа

- Основной агент сверяет отчёт с критерием выхода этапа и сообщает владельцу итог кратко: что сделано, какие файлы затронуты, всё ли по критериям.
- Обновляются FRONTEND_CURRENT_STATE.md и раздел 9 PRODUCT_SPECIFICATION.md, если этап менял описанное там состояние.
- Коммиты — с осмысленными сообщениями, по соглашению репозитория (conventional commits, как в истории).

## Общие ограничения

- Секреты и пароли — только через `.env`, никогда в коде, логах, коммитах.
- Новых зависимостей и фреймворков без необходимости не добавлять; версии и идиомы — как в существующем коде.
- Тесты писать в существующем стиле (Vitest на фронте, JUnit/MockMvc на бэке); новые тестовые инфраструктуры не плодить.
- Это пет-проект, но стандарт качества — «показывающий реальные намерения»: проверки зелёные, критерии выхода выполнены, красивые хаки с TODO не остаются.
