# BACKEND_FRONTEND_CONTRACT

## 1. Назначение

Этот документ фиксирует контракт взаимодействия между frontend (React + Vite + TypeScript) и backend (Java + Spring) для Leetcode Tracker.

Цель контракта:

- обеспечить предсказуемое и стабильное API-поведение;
- дать единые правила форматов запросов и ответов;
- минимизировать регрессии при параллельной разработке frontend и backend.

## 2. Область действия

Контракт покрывает:

- аутентификацию и сессию;
- справочники (сложности, состояния, темы, политики интервалов);
- задачи и связь задач с темами;
- пользовательские задачи;
- историю повторений и очередь повторов;
- статистику для экрана аналитики.

## 3. Базовые правила API

| Правило | Значение |
|---|---|
| Базовый префикс | `/api/v1` |
| Формат данных | `application/json; charset=utf-8` |
| Формат полей JSON | `camelCase` |
| Формат дат времени | ISO 8601 UTC |
| Формат локальной даты | `YYYY-MM-DD` |
| Идентификаторы | `number` (int64) |

## 4. Версионирование и совместимость

- Любые breaking changes в API допускаются только при переходе на новый префикс версии (`/api/v2`).
- Добавление новых необязательных полей в ответы не считается breaking change.
- Удаление или переименование существующих полей в рамках одной версии запрещено.

## 5. Аутентификация и авторизация

| Аспект | Контракт |
|---|---|
| Access token | Bearer JWT в заголовке `Authorization` |
| Refresh token | HttpOnly cookie, обновляется через отдельный endpoint |
| Контекст пользователя | Все `me`-маршруты работают только для аутентифицированного пользователя |
| Ошибка доступа | `401 Unauthorized` или `403 Forbidden` с унифицированным телом ошибки |

## 6. Единый формат ответа

### Успешный ответ

| Поле | Тип | Описание |
|---|---|---|
| data | object/array | Полезная нагрузка |
| meta | object | Пагинация, фильтры, служебная информация |

### Ошибка

| Поле | Тип | Описание |
|---|---|---|
| error.code | string | Машинный код ошибки |
| error.message | string | Краткое описание |
| error.details | array | Детали валидации или контекста |

## 9. Контракт по задачам

### 9.1 Глобальный каталог задач (TASKS)

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/v1/tasks` | Поиск и фильтрация задач |
| GET | `/api/v1/tasks/{taskId}` | Детали задачи |
| POST | `/api/v1/tasks` | Создание задачи |
| PATCH | `/api/v1/tasks/{taskId}` | Частичное обновление задачи |

Поля задачи в контракте:

- id
- sourceType
- sourceProblemId
- title
- description
- link
- difficultyId
- createdAt
- updatedAt

Правила идентичности задачи:

- Backend поддерживает внутренний `identityKey` для безопасной дедупликации TASKS.
- Frontend не передаёт и не отображает `identityKey`.
- Для задач из внешнего источника (например LeetCode) идентичность определяется стабильным ключом источника.
- Для пользовательских задач backend применяет нормализацию и формирует внутренний ключ идентичности.

### 9.2 Связь задач с темами (TASK_TOPICS)

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/v1/tasks/{taskId}/topics` | Список тем задачи |
| PUT | `/api/v1/tasks/{taskId}/topics` | Полная замена списка тем |

Контрактный инвариант:

- Пара `(taskId, topicId)` должна быть уникальной.

## 10. Контракт по пользовательским задачам

### 10.1 USER_TASKS

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/v1/me/tasks` | Список задач пользователя |
| GET | `/api/v1/me/tasks/{userTaskId}` | Детали отслеживаемой задачи |
| POST | `/api/v1/me/tasks` | Начать отслеживание задачи |
| PATCH | `/api/v1/me/tasks/{userTaskId}` | Обновить заметки или ручные настройки |
| DELETE | `/api/v1/me/tasks/{userTaskId}` | Прекратить отслеживание |

Поля user-task в контракте:

- id
- userId
- taskId
- currentStateId
- lastReviewDate
- nextReviewDate
- userNotes
- createdAt
- updatedAt

Контрактные инварианты:

- `(userId, taskId)` уникальна.
- В `me`-маршрутах `userId` всегда определяется сервером из токена.

### 10.2 Динамический жизненный цикл TASKS (скрыт от конечного пользователя)

Контрактное поведение при создании отслеживания задачи:

- Frontend отправляет intent "добавить задачу в мой кабинет".
- Backend внутри транзакции пытается найти существующую TASKS по внутреннему ключу идентичности.
- Если запись TASKS найдена, backend не создаёт дубль и сразу создаёт USER_TASKS.
- Если запись TASKS не найдена, backend создаёт TASKS и затем создаёт USER_TASKS.
- Для пользователя сценарий единый: задача просто добавилась.

Контрактное поведение при удалении из кабинета:

- Frontend отправляет intent "удалить задачу из моего кабинета".
- Backend удаляет только связь USER_TASKS для текущего пользователя.
- Далее backend проверяет, остались ли ссылки на эту задачу в USER_TASKS других пользователей.
- Если ссылки есть, TASKS не удаляется.
- Если ссылок больше нет, backend удаляет orphan-запись из TASKS и связанные TASK_TOPICS.
- Для пользователя сценарий единый: задача просто удалилась из его кабинета.

Требования к надёжности:

- Операции add/remove выполняются в транзакции.
- Backend обязан быть устойчив к гонкам параллельных запросов.
- Повторный запрос удаления одного и того же user-task должен быть идемпотентным с пользовательской точки зрения.

### 10.3 Очередь повторений

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/v1/me/review-queue` | Задачи к повторению на дату |

Параметры запроса:

- date (опционально, `YYYY-MM-DD`)
- по умолчанию backend использует текущую дату в UTC.

## 11. Контракт по повторениям и истории

### 11.1 USER_REVIEWS

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/v1/me/reviews` | История повторений пользователя |
| POST | `/api/v1/me/tasks/{userTaskId}/reviews` | Зафиксировать результат повторения |

Поля review в контракте:

- id
- userTaskId
- stateId
- reviewedAt
- intervalDays
- nextReviewDate
- reviewText
- createdAt

Критичные транзакционные требования:

- Создание записи в USER_REVIEWS и обновление текущего среза в USER_TASKS выполняются атомарно.
- После успешного POST review backend обязан вернуть обновлённый USER_TASKS и созданный review в одном ответе.
- USER_REVIEWS остаётся источником истины для аналитики.

## 14. Идемпотентность и защита от дублей

- Для мутаций, чувствительных к повторной отправке (особенно POST review), frontend передаёт `Idempotency-Key`.
- Backend гарантирует, что повторный запрос с тем же ключом не создаёт дубликаты.

## 15. Безопасность и операционные правила

- Все production-вызовы только по HTTPS.
- CORS ограничивается доверенными origin frontend-приложения.
- Логи не должны содержать пароли и refresh-токены.
- Каждый ответ содержит `requestId` для трассировки.

## 16. Правила эволюции контракта

- Любое изменение endpoint или схемы ответа сначала фиксируется в этом документе.
- Backend и frontend синхронно обновляют DTO и тесты контрактов.
- До внедрения в коде изменение считается незавершённым, если не описано в этом файле.
