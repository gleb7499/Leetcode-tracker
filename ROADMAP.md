# Дорожная карта проекта (долгосрочный план)

Фиксирует пошаговый путь от текущего состояния к завершённому open-source продукту для локального запуска.
Канонические источники: [PRODUCT_SPECIFICATION.md](PRODUCT_SPECIFICATION.md), [BACKEND_FRONTEND_CONTRACT.md](BACKEND_FRONTEND_CONTRACT.md), [DATABASE_DIAGRAM.md](DATABASE_DIAGRAM.md).

## Цель

Завершённый продукт = открытый репозиторий, который любой может склонировать и запустить локально (через Docker) одной командой. Продукт позиционируется как **local-first**: все данные пользователя живут только на его компьютере. Предназначение — портфолио и продуктовый/технический опыт, не монетизация. Облачный деплой не является целью, но архитектура должна быть container-ready: при желании владелец может развернуть проект на собственном сервере, поменяв только `.env`.

Следствия позиционирования:

- Docker-compose — основной способ запуска для пользователя.
- Вся конфигурация — через переменные окружения (12-factor): никаких захардкоженных localhost/секретов в коде; `.env.example` с разумными дефолтами «из коробки».
- Email-отправка конфигурируется SMTP-настройками: заданы (`MAIL_HOST/PORT/USER/PASS`) — письма уходят через реальный SMTP-релей (Gmail/SendGrid/Mailgun), не заданы — dev-fallback, OTP падает в лог. Локально для реалистичной проверки писем — опциональный контейнер Maildev/Mailhog в docker-compose.
- JWT-секреты и настройки — только из `.env`.
- «Синхронизация между устройствами» не является целью — данные локальны, бэкап — это экспорт/импорт файла.

## Этап 0. Подготовка backend-каркаса

- Spring Boot проект: зависимости (Web, Data JPA, Validation, Security, PostgreSQL driver, Flyway).
- Конфигурация: `application.yml`, переменные окружения, разумные дефолты для локального запуска.
- Базовая структура пакетов: `controller` / `service` / `repository` / `entity` / `dto` / `config`.
- Health-check endpoint (`/api/health`), CORS-настроен под фронтенд.
- Критерий выхода: приложение стартует, `./gradlew test` зелёный.

## Этап 1. База данных и Docker-окружение

- Docker-compose: PostgreSQL + backend + frontend (сборка фронта через nginx или dev-профиль) + опциональный Maildev (локальный SMTP с веб-интерфейсом для проверки писем).
- Миграции Flyway по [DATABASE_DIAGRAM.md](DATABASE_DIAGRAM.md): reference-таблицы (difficulty, sources, status), operational (`users`, `tasks`, `task_reviews`, `user_settings`), reporting (`task_stats`).
- Ограничения целостности из раздела «Integrity constraints» — на уровне БД, не только JPA.
- Одна команда запуска: `docker compose up`.
- Критерий выхода: с чистого клона `docker compose up` поднимает работающий стек, миграции накатываются с нуля.

## Этап 2. Auth API

- Эндпоинты MVP из контракта: register, login, logout, email-verification (OTP), сброс/смена пароля.
- Spring Security + JWT (access/refresh), BCrypt для паролей.
- Отправка email через `spring-boot-starter-mail` + `JavaMailSender`: SMTP берётся из env; при незаданном SMTP — fallback, OTP пишется в лог. Тесты покрывают оба режима.
- Единая модель ошибок из контракта (раздел «Error model»).
- Тесты: unit + MockMvc интеграционные на каждый эндпоинт.
- Критерий выхода: полный auth-flow проходит через API тестами: register → verify → login → access/refresh → logout.

## Этап 3. Tasks API + интервальное повторение

- CRUD задач по контракту (модель Task с `source`, `sourceMeta`, `scheduleMode`).
- Парсинг URL LeetCode на бэкенде (валидация + извлечение slug/id).
- Эндпоинт текущей review-очереди: задачи, назначенные на сегодня по алгоритму из PRODUCT_SPECIFICATION.md (раздел 7).
- Запись результатов повторения (`task_reviews`), пересчёт следующей даты по интервальному алгоритму, статусы из раздела 4.3 PRODUCT_SPECIFICATION.md.
- Критерий выхода: сценарий «добавил задачу → повторил → дата сдвинулась» проходит интеграционным тестом.

## Этап 4. Статистика

- Reporting-таблица `task_stats`, заполняемая при каждом review.
- Эндпоинты прогресса: streak, общий прогресс, распределение по сложностям/источникам (раздел 4.4 PRODUCT_SPECIFICATION.md).
- Критерий выхода: данные статистики совпадают с ручной проверкой на тестовом наборе review-сессий.

## Этап 5. Интеграция фронтенда с backend

- Слой API-клиента на фронтенде, замена local storage-адаптера на HTTP (auth, tasks, review, stats) по контракту.
- Обработка ошибок API в существующих UI-потоках, токены в безопасном хранилище, рефреш при 401.
- Этапная замена по доменам: auth → tasks → review → stats.
- Критерий выхода: все существующие тесты фронтенда проходят против реального backend в docker-compose, локальное хранилище удалено.

## Этап 6. Настройки и бэкап данных

- `user_settings` на бэкенде + экран настроек на фронтенде (раздел 8 PRODUCT_SPECIFICATION.md).
- Экспорт/импорт данных пользователя в файл (JSON) — форма бэкапа для local-first продукта.
- Удаление аккаунта, смена пароля.
- Критерий выхода: экспорт → сброс БД → импорт восстанавливает все задачи, review-историю и статистику.

## Этап 7. Готовность продукта для клонирования

- README как главный вход: что это, скриншоты, `docker compose up`, оба режима email (Maildev локально / реальный SMTP через `.env`), как сделать бэкап, как развернуть на собственном сервере.
- CI (GitHub Actions): backend tests + build, frontend typecheck/lint/test/build, блокировка merge при красном.
- `docker-compose.yml` + `.env.example` проверены на чистом клоне (вручную и по возможности CI).
- Лицензия open-source (MIT или иная — выбрать).
- Критерий выхода: человек с чистой машиной (Docker только установлен) клонирует репозиторий и за 5 минут имеет работающее приложение.

## Этап 8. Полировка

- Обработка edge-cases: истёкший OTP, потерянный refresh, дубли задач, пустая review-очередь.
- Скорость: индексы под запросы review-очереди и статистики, N+1-запросы.
- UX-полировка по скриншотам-аудиту из корня.
- Критерий выхода: чек-лист всех экранов из раздела 8 PRODUCT_SPECIFICATION.md пройден, известных багов нет.

## После завершения (опционально, не цель)

- Уведомления локальные (browser notifications) о сроках повторения.
- Расширенная аналитика.
- Мобильный контур.

## Правила работы по плану

- Этап считается завершённым только когда выполнен его критерий выхода.
- Новый этап не начинается, пока текущий не закрыт (исправления багов — исключение).
- Изменения API — только через [BACKEND_FRONTEND_CONTRACT.md](BACKEND_FRONTEND_CONTRACT.md), обе стороны меняются синхронно.
- По завершении каждого этапа — обновлять [FRONTEND_CURRENT_STATE.md](FRONTEND_CURRENT_STATE.md) и статус в PRODUCT_SPECIFICATION.md (раздел 9).
